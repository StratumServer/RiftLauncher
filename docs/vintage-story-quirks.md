# Vintage Story quirks

Field knowledge for anyone touching the game catalog, a fork of the client, archive extraction, the installer, the ModDB API, or account login. Everything below is verified against this codebase's own code, comments, tests, or open issues; nothing here is general Vintage Story lore that isn't also load-bearing somewhere in RiftLauncher. Closes #31.

## Catalog

**`filesize` is a human string, not a number.** `stable.json`/`unstable.json` (`https://api.vintagestory.at/{stable,unstable}.json`) publish `filesize` as `"590.5 MB"`, not a byte count. Nothing in the launcher reads it today: `src/renderer/src/features/versions/hooks/useGameVersionCatalog.ts:6-7` documents the full raw shape in a comment but its `RawPlatform` type picks out only `filename` and `urls`, and `toBuild` (line 25) reads nothing but `filename` and `urls.cdn`. The first pre-download size check or size display written against this field will mis-parse it if it assumes a number. See issue #31.

**Per-OS entries carry `filename`, `md5`, and `urls.cdn`/`urls.local`.** Each platform key (`windows`, `linux`, `mac-arm64`, `mac-x64`) in a catalog entry has its own filename and MD5, plus two download URLs. `src/ipc/artifactVerification.ts:44` reads both `urls.cdn` and `urls.local` as candidate match targets when verifying a downloaded file's hash against the official manifest; `useGameVersionCatalog.ts` uses only `urls.cdn` to build the actual download.

**Older Linux entries ship as `vs_archive_<v>.tar.gz`, one archive for client and server, sharing the same wrapping folder as everything else.** Per issue #31: "Older Linux entries ship as `vs_archive_<v>.tar.gz`, one archive for client and server, same wrapping folder. The new extraction path handles the shape but has never been run against a real one." The generic flattening logic in `src/ipc/workers/extraction.ts` (`contentRoot()`, see Archive below) would handle this shape if it showed up, and `isTarGzName` in `src/ipc/validation.ts` routes any `.tar.gz`/`.tgz` name to the tar extractor regardless of the specific filename, but no test in this repo exercises the literal `vs_archive_` name against a real download. Treat this path as plausible, not proven.

**`assets/version-<v>.txt`, the zero-byte marker the game itself checks at startup, does not exist in 1.18.15 and older.** It only appears in later builds. Any install-verification code must not assume it exists. The current detection code sidesteps the problem entirely rather than working around it: `src/domain/versions/detect.ts` and `src/domain/versions/gameExecutable.ts` verify an install by looking for the game's executable (`expectedGameExecutables`, `gameExecutable.ts:35-44`), never for the marker file, which is exactly why this trap has never been triggered. See issue #31.

## Forks

**Optimum is a client-side fork, and what it publishes is an overlay rather than a client.** The game is proprietary, so the fork cannot ship one: what it ships instead is `Optimum-v<version>-<rid>-overlay.tar.gz`, carrying donor assemblies, a patcher, a CLI and its own shaders and language files, and the patch runs on the player's machine against a vanilla build they already have. `optimum patch --game-dir <abs> --overlay <abs> --json` writes nothing outside the game folder, keeps a copy of the four assemblies it replaces under `.optimum/vanilla/`, and prints one compact JSON object per line on stdout: `progress` up to 99, `log`, and exactly one terminal `result` carrying `ok` or a `reason` from a closed set. Exit 0 is success, 2 is bad input, and 1 is everything else. Sources: <https://github.com/StratumServer/Optimum>, its `Optimum.Bootstrap.Core` and `Optimum.Cli` projects, and <https://mods.vintagestory.at/optimum>.

**No overlay has been published yet, so the launcher offers nothing and says so.** Release v0.3.14 carries no assets, and no workflow runs the packaging script, so `optimum-manifest.json` is not there to read and the VS Versions page shows Optimum as a disabled choice with one line under it. The same line appears on a machine the published manifest is not for: one manifest per release describes one platform, so until Optimum builds per RID, Windows stays unoffered. The flow degrades to "no Optimum offered" rather than to an error, which is why none of this is gated behind a flag.

**A built Optimum folder registers as a normal VS Version, because the fork's own packaging keeps the vanilla file name.** `scripts/package-linux.sh` copies the vanilla-named launcher next to the branded one on purpose, so the folder holds both `Vintagestory` and `Optimum` and `expectedGameExecutables` (`src/domain/versions/gameExecutable.ts`) matches it with nothing added. Its launcher also takes `--dataPath`, which is what `buildGameLaunchPlan` passes.

**What identifies the fork is the `LongGameVersion` suffix, not the file name.** The IL patch appends `" + Optimum v<version>"` to `GameVersion.LongGameVersion` (`Optimum.Patcher/api-patcher.cs`, `PatchGameVersionLabel`), and the patch path also logs `[Optimum] Optimum v0.3.14`. `extractOptimumVersion` in `src/domain/versions/detect.ts` reads that marker, off the same version grammar the game version is read with, and the label builder in `src/domain/naming.ts` turns it into `1.22.7 Optimum 0.3.14`. The file names in the folder are deliberately not consulted: anyone can name a file `Optimum`, while the suffix comes from the patched DLL that actually changes how the build behaves. The marker text is cut out of the output before the game version is read off it, because the patch chatter is printed before the client answers and the fork's own `0.3.14` would otherwise be taken for the game's number on any output holding no bare version line.

**The manifest's `supportedGameVersions` is advisory, and the launcher is the only thing enforcing it.** `GamePatcher` never reads `optimum-manifest.json` and never compares a game's assemblies to an expected hash, so pointing the patch at a build Optimum was not made for surfaces as a `patch-conflict`, or slips through. The launcher checks the list itself before it spawns anything (`supportsGameVersion` in `src/domain/optimum/plan.ts`, checked again in `src/ipc/optimumInstall.ts`), and `targets[]` carries `expectedInputSha256` and `expectedOutputSha256` fields the packaging script never writes, so neither can be used for that check today. What carries provenance instead is `files[]`: every file staged out of the archive is hashed against it before the CLI runs, which is what makes the archive's own hash reach the donors, the patcher and the CLI individually.

**Removing Optimum cannot give back a byte-identical vanilla install, and the launcher says so rather than pretending.** `--rollback`, and the launcher's own restore, put back the four assemblies from `.optimum/vanilla/`. Neither removes `Optimum.Api.Contracts.dll`, the shaders it overlaid, or the language keys it merged into `assets/game/lang/*.json`; the launcher removes the first and leaves the other two, because undoing them would mean keeping a pristine copy of a gigabyte-sized install. The confirmation dialog spells that out. RiftLauncher does the restore itself rather than running the CLI with `--rollback`, so removing Optimum needs no download, no staged overlay and no .NET runtime.

**A killed patch leaves `.dll.tmp-<guid>` files at the game root and under `Mods`.** The CLI deletes them in `finally` blocks, which a SIGKILL does not run. They are inert, and nothing in the launcher removes them today.

**The overlay is framework-dependent `net10.0`, so a player without the .NET 10 runtime gets a refusal rather than a patch.** `optimum.runtimeconfig.json` asks for `Microsoft.NETCore.App 10.0.0` and the apphost is a plain ELF or PE, not a self-contained build. The launcher asks the CLI for its own version before promising anything and reports `runtime-missing` when that fails, reusing the docs link the missing-.NET notification already opens.

**The Optimum flow can be pointed at a loopback origin for a live check.** Setting `RIFTLAUNCHER_OPTIMUM_ORIGIN` to `http://127.0.0.1:<port>/` makes the launcher read `optimum-manifest.json` and the overlay archive off that origin under the same names, which is how the whole install can be exercised on a machine with no published payload to fetch. Nothing else moves: the archive is still checked against the hash that manifest publishes, every staged file against its own, the game folder still goes through `assertManagedPath`, and the child process keeps its bounds. It is honoured only for `http://127.0.0.1:<port>` with no path, nothing in a shipped build sets it, and a build that finds it set logs a warning. See `optimumTestOrigin` in `src/ipc/validation.ts`.

**Optimum reports the vanilla game version, and versions itself on a separate 0.x line.** The number a registered Optimum build carries is the game version it was built against (1.22.7 today), which is what mods target, so nothing compatibility-related needs to know the build is a fork. Its own version, 0.3.14 today, only ever shows up in the label. There is no artefact called "Optimum 1.22.7", and its ModDB releases tag the game version as `0.0.0`, so that API carries no usable game-version metadata either.

## Archive

**A single wrapping folder gets flattened.** `contentRoot()` in `src/ipc/workers/extraction.ts:112-131` steps into an archive's contents only when the root holds exactly one entry and it is a directory; anything else (including an already-flat server archive) is left untouched. It is applied only when the caller asks for it (`unwrapSingleRootFolder`, which the game version install passes and the backup restore does not: `copyTree(unwrapSingleRootFolder ? contentRoot(extractionRoot) : extractionRoot, outputPath)`). Covered by `tests/ipc/extraction.test.ts` ("unpacks a wrapped archive straight into the target folder" / "leaves a flat archive flat").

**Zero-size entries have to survive extraction as zero-size files, not be treated as errors or skipped.** `tests/ipc/extraction.test.ts:132-142` builds an archive containing an empty `assets/version-1.22.6.txt` (the version marker from the Catalog section above) and asserts the extracted file exists with `size === 0`. `validateTree` in `src/ipc/workers/extraction.ts` counts zero-byte files explicitly rather than special-casing them away.

**Vintage Story's tars have NUL bytes in their numeric header fields, which p7zip rejects and node-tar (and GNU tar) accept.** This is one of the reasons the launcher reads `.tar.gz` with the `tar` npm package, and it was the reason it never routed game archives through 7-Zip even while 7-Zip was still bundled. Since the launcher dropped `node-7z` and `7zip-bin` (issue #222), only two formats are read at all: gzipped tar through `tar` (`extractTarGz` in `src/ipc/workers/extraction.ts`, for game builds and for the backups the launcher writes) and zip through `yauzl` (`extractZip`, same file, for the backups made before that change). Anything else is refused by `validateArchive` in `src/ipc/archiveValidation.ts` rather than handed to a reader that would have to guess at it.

## Installer

**The installer is Inno Setup 6.4.x, and only that family is read.** `src/domain/inno/version.ts` refuses any version string outside 6.4 (with sub-notes on layout differences between 6.4.0.1, 6.4.2 and 6.4.3, reflected in `src/domain/inno/script.ts`'s field-dropping logic at various points in the file).

**Running the real installer silently still shows a MsgBox that `/SUPPRESSMSGBOXES` cannot suppress, because it comes from `InitializeSetup`, which runs before Inno gets to the flags that gate its own message boxes.** It is keyed off an HKCU uninstall registry key the installer itself writes on every run, so a second silent run trips over the first one's leftovers. This is issue #8. Documented at `src/domain/inno/extract.ts:4-8` and again at `src/ipc/handlers/pathsHandlers.ts:46-49`: "a pre-existing uninstall key makes InitializeSetup show a MsgBox that /SUPPRESSMSGBOXES cannot answer, the silent run hangs on it, and every run writes that key back for the next install to trip over."

**The bundled runtime sub-installer (the .NET 7 Desktop Runtime that 1.18.15 pulls in) can hang outright rather than fail fast.** On a clean `windows-latest` GitHub Actions runner it hung until the job died at its 30-minute ceiling with the installer still alive as an orphan process. This is issue #55, and it is why `RUN_INSTALLER` (`src/ipc/handlers/pathsHandlers.ts`) bounds the fallback installer run at 15 minutes with a process-tree kill rather than trusting the surrounding job timeout.

**RiftLauncher's answer to both of the above is to extract the installer's payload directly, without ever running its script, falling back to actually spawning the installer only when the payload reader refuses the file's format.** `EXTRACT_INSTALLER_PAYLOAD = true` in `src/ipc/handlers/pathsHandlers.ts:42-56` is the switch; the extraction itself lives in `src/domain/inno/extract.ts` (see the architecture doc's "Inno reader" section for how it works). When the reader throws `format-refused`, `pathsHandlers.ts:428-433` falls back to `spawnInstaller`, which runs the real `.exe` with `/VERYSILENT /SUPPRESSMSGBOXES /NORESTART /CURRENTUSER /NOICONS`, the exact path issue #8 documents as fragile: "The original path: run the installer silently and hope no dialog is waiting. Kept for the file this reader cannot follow."

## ModDB

**Every v1 endpoint answers a real HTTP 200 whether the call succeeded or not; the actual result lives in a `statuscode` field that is itself a string, `"200"` on success, never a bare number.** `src/domain/mods/moddb.ts:4-9` states it directly, and the gate is enforced in code: `SUCCESS_STATUS_CODE = "200"` (line 36), checked before anything else in the body is trusted (`readV1`, lines 71-86). A caller that skips this and trusts the body outright silently gets `undefined` back from every field on every application-level error.

**`/api/mods` has no pagination and returns the whole catalog, roughly 3.5 MB today for about 8000 mods.** That used to sit right up against the launcher's generic 4 MB IPC response ceiling (`MAX_RESPONSE_BYTES` in `src/ipc/validation.ts:9`), which is issue #24: "The gap is one catalog growth spurt wide. When it trips, search dies with no fallback UI." That one endpoint now carries its own allow-listed ceiling instead, `MAX_MODS_CATALOG_RESPONSE_BYTES = 16 * 1024 * 1024` (`validation.ts:17`), applied as a per-rule override on the `/api/mods` prefix (`validation.ts:47`). The headroom is years wide rather than months, but it is still a fixed number and the API still offers no server-side fix; there is nothing to opt into.

**`/api/updates` reports its `updates` map as a JSON object when it has entries and as an empty array `[]` when it does not**, a PHP `json_encode` artifact (PHP has one array type for both, and it guesses from whichever is present). This is documented as a trap for whoever writes the first reader for that endpoint, not as something already handled: `src/domain/mods/moddb.ts:17-21` calls it out explicitly and notes the launcher does not call `/api/updates` today. A future reader needs to accept both shapes for the same field.

**`modinfo.json` `dependencies` is a map of mod id to the lowest acceptable version, and `"*"` and the empty string both mean any version** (https://wiki.vintagestory.at/Modding:Modinfo). `parseModInfo` reads it (`src/domain/mods/modinfo.ts`), and `checkModHealth` (`src/domain/mods/health.ts`) checks one level of it against the folder: declared but absent, present at too low a version, or present but renamed out of the game's way. Two rules there are worth knowing before touching any of it. `game`, `survival` and `creative` ship inside the game, so a dependency on one is a floor against the game's own version and never an archive to install; the list is `GAME_BUNDLED_MODIDS`. And the comparison is `semver` on both sides with no coercion, so a mod shipping a two-part ("1.0") or four-part ("1.2.3.4") version has that one comparison skipped rather than failed, the same refusal `findModUpdate` already makes. Transitive resolution is still not implemented, and the modpack import still ignores dependencies entirely (`src/domain/mods/importModpack.ts`): a manifest lists every mod it wants explicitly.

**Public mod pages are built from `assetid`, never `modid`.** `src/renderer/src/features/mods/hooks/useExternalLinks.ts:3-10` builds every "view on the ModDB" link as `https://mods.vintagestory.at/show/mod/${assetid}`; `modid` is used only for API calls (`/mod/{id}`), never for a page URL. The `urlalias` field is typed on `DownloadableModOnListType`/`DownloadableModType` (`src/global.d.ts:158,172`) but is not actually read anywhere in the codebase today; it is dead in practice, not a second valid way to build the URL.

**Compatibility tags are declarative, author-set checkboxes, never enforced against the mod's own `modinfo.json`, and they go stale as authors move on to other projects.** That is why the launcher's own verdict for "no tag mentions this game version" is named `undeclared`, not `incompatible`: `src/domain/mods/compatibility.ts:1-14` states the reasoning directly, that the launcher "does not know it will not work, only that nobody has said it will." The three verdicts are `declared` (exact tag match), `same-minor` (a tag shares the Major.Minor series), and `undeclared`.

**An empty tag or identifier list on `/api/mods` comes back as `[""]`, an array holding one empty string, instead of `[]`.** It is an artifact of a SQL `GROUP_CONCAT` returning `NULL` for nothing to concatenate, then exploded on a comma regardless of whether it held anything. `/api/mod/{id}` does not share the bug for the same field on the same mod, which is why the fix lives in the list reader: `cleanStrings()` in `src/domain/mods/moddb.ts:48-62` trims and drops empty entries, applied to both `modidstrs` and `tags` (line 102).

## Auth

**Login is two passes when two-factor is enabled, never more.** The first pass to `POST auth3.vintagestory.at/v2/gamelogin` can answer `requiretotpcode` with a `prelogintoken`; the second pass sends that token back with the six-digit code. `src/domain/account/login.ts` enforces this at the type level, not just by convention: `interpretFirstPass` (line 174) is the only function that can return `CompleteTwoFactor`, the one verdict that asks for another request, and `interpretSecondPass` (line 195) returns a type with no such member, so a second pass answering `requiretotpcode` again is read as a refusal instead of an invitation to try a third time. The module's own heading for this section is "No retry, by construction" (lines 17-28).

**The auth server rejects requests carrying Electron's Chromium-flavoured `net.request` metadata (its `sec-fetch-*` headers and Chrome User-Agent), so login goes over a plain Node `https` transport instead.** This is issue #76. `src/ipc/network.ts:106-116` names it directly: a Node-https-transport twin of the normal bounded-request function exists "for the one endpoint that refuses Electron's Chromium-flavoured net.request... the auth service rejects credential posts that carry net.request's sec-fetch-\* metadata and Chrome User-Agent, neither of which request.setHeader can strip." The function deliberately sends no `User-Agent` header at all, matching what the game's own .NET `HttpClient` sends (`network.ts:132-133`).

**`entitlements` can legitimately be `null`, and the code must accept that rather than treat it as a bad response.** A `gamelogin` response for an account with no entitlements answers `entitlements: null`, and the real game client writes that null straight into `ClientSettings.Entitlements`. `nullableAccountString()` in `src/domain/account/credentials.ts:106-118` exists specifically to allow this: "Refusing null here would turn a login the server accepted into a false 'wrong credentials' diagnosis, which is exactly what issue #74 was."

**The login request includes a `gameloginversion` field**, matching the real game client's own login contract rather than a launcher-invented guess at one. `src/ipc/handlers/loginRequestBody.ts:12-26` documents it as decompiled directly out of `VintagestoryLib.dll` 1.22.6's `DoLogin`, which builds its request from exactly five fields in a fixed order (`email`, `password`, `totpcode`, `prelogintoken`, `gameloginversion`). The constant, `GAME_LOGIN_VERSION = "1.22.6"`, has no automated reminder to update it: "This needs to move every time the launcher starts targeting a newer stable game version: it is not read from anywhere, so nothing else will remind you to update it."

**The password is never stored and a failed login is never retried automatically.** `AccountSecrets` (`credentials.ts:21-25`) holds only `sessionKey`, `sessionSignature` and `mptoken`; there is no password field anywhere past the request that sends it. `src/ipc/handlers/accountHandlers.ts:30-31` states it as a rule for the handler itself: "The password is a parameter and nothing else: it is never held in a field, never logged, and never survives the call." The no-retry rule is the same one covered under two-pass 2FA above: the types make a third request unreachable, and `accountHandlers.ts:82-83` notes "There is no retry, and the shape of the flow is what rules one out."

## Launch outcome

**A completed game process proves nothing about whether the session went well, and only a non-zero exit code is treated as evidence worth mentioning, never as a launch failure.** `src/domain/ports.ts:292-295` states the underlying rule: "An exit code is reported for the record and never read as a verdict: Vintage Story exits non-zero often enough that treating that as a failed launch would report an error to a player who just finished playing." The renderer layer adds one asymmetric exception on top of that: `pickPlayOutcomeNotification` in `src/renderer/src/utils/playOutcomeNotifications.ts:41-43` shows nothing when the game exits cleanly, but does surface a "the game exited with errors" notice when the exit code is non-zero and non-null, described as "a crash worth telling the player about." In other words: the launcher can flag a probable failure, but a clean or missing exit code is never read as proof the game actually ran well, only as absence of a signal that it didn't. `gameHandlers.ts:103,126` reinforces the same asymmetry for stderr: it is logged (truncated to 2 KiB) for the record, but never fails the outcome on its own.
